# AI 视频客服 Demo · 云端实测使用手册

**版本**：v1.2 实测版（2026-09-29 补充：数字人 ↔ 文字会话**同屏联动**取证；v1.1 为坐席接管外呼 + 质检监听 + 三角色同屏）
**日期**：2026-09-29
**测试环境**：仙宫云 GPU 实例（RTX 4090D / 24GB）
**结论先说**：文字客服链路（客户 ↔ AI ↔ 人工坐席 ↔ 质检）在云端四个角色全部跑通并截图取证；坐席不仅能旁听，还能**主动对房间内所有人说话**（接管外呼）；数字人（LiveTalking + Wav2LiP）GPU 推理已跑通，并且本轮通过 **MJPEG 降级通道**把数字人画面与文字会话放进了同一屏 —— 浏览器 `<img>` 实测渲染 576×768 的 LiveTalking 帧，文字提问触发 `/human` 后口部 ROI 差分从基线 5.31 升到 8.01（1.51×），肉眼复核口型随文本张合（§5.5）。**但仙宫云端口代理不转发 UDP，实时 WebRTC 画面仍直连不通**，该通道只有 ≈3fps 且**无音频**。

## 1. 系统构成

| 组件 | 作用 | 端口 | 实测状态 |
|------|------|------|---------|
| LiveKit Server | 房间/信令/媒体 SFU | 7880(WS) / 7881(WHIP-WHEP) | ✓ `--dev` 模式运行 |
| LiveKit Agents worker | AI 客服进程，注册 RPC 方法 `ask` | 8081 | ✓ 已注册 |
| Ollama + qwen2.5:3b | 大模型推理 | 11434 | ✓ GPU 推理 |
| Token+Web 服务 | 发 token、托管页面、创建 dispatch | 3210 | ✓ |
| LiveTalking | 数字人唇形渲染（Wav2LiP） | 8010 | ✓ GPU 推理，画面见 §5 |
| avatar_bridge.py | 同机 aiortc 常驻观看者 → `latest.jpg` | — | ✓ §5.5 同屏联动 |

**角色模型**：同一个房间 `cs-demo` 里可有多个身份 —— `customer`（客户）、`human-seat`（人工坐席）、`quality-admin`（质检/管理员）、`agent-AJ_xxx`（AI 客服，由 worker 自动派生）。页面地址加 `?name=xxx` 即以该身份入房，**发送按钮的行为按角色分流**：

| 角色 | 入房方式 | 「发送」做什么 | 收得到什么 |
|------|---------|---------------|-----------|
| `customer` | `/start`（建房 + 建 dispatch + 发 token） | RPC `ask` → Ollama → 同步答案 | 自己的 RPC 答案 + 房间 `[转写]` |
| `human-seat` / `quality-admin` / 任意自定义角色 | `/token?name=`（仅发 token） | `sendText` 广播到 topic `transcript`，前缀 `[角色名]` | 房间内所有人的 `[转写]` 与广播 |
| `agent-*` | dispatch 自动拉起 | 问答后向房间广播 `[转写]` | 客户的 RPC 请求 |

也就是说：**客户是"问 AI"，其他角色是"对房间里所有人说话"** —— 这就是 PRD 里"人工接管外呼"的最小可运行版本。

## 2. 云端访问方式（关键前提）

仙宫云的端口代理规则：**容器内任意端口 P，公网地址为**

```
https://{实例ID}-{P}.container.x-gpu.com
```

本次实例 ID 为 `<实例ID>`，所以：

| 用途 | 公网地址 |
|------|---------|
| 客服页面 | `https://<实例ID>-3210.container.x-gpu.com/` |
| LiveTalking 控制台 | `https://<实例ID>-8010.container.x-gpu.com/admin.html` |
| LiveKit 信令 | `wss://<实例ID>-7880.container.x-gpu.com` |

**重要限制**：该代理只提供 HTTPS / WSS（TCP 通道），**不转发 UDP**。WebRTC 的媒体面走 UDP，因此浏览器直连数字人时信令能握手、ICE 卡在 `connecting`。服务端代码已按 Host 头自动推导公网 wss 地址：

```js
function publicLkUrl(req) {
  const host = req.headers.host || '';
  if (host.startsWith('localhost') || host.startsWith('127.')) return 'ws://localhost:7880';
  return 'wss://' + host.replace(/-\d+\./, '-7880.');
}
```

## 3. 部署步骤（可复跑）

```bash
# 1) LiveKit Server（二进制从 GitHub Releases 取，Docker Hub 不可用）
tar -xzf livekit-server.tar.gz && ./livekit-server --dev &

# 2) Ollama（GitHub release 二进制）+ 模型
tar -xzf ollama-linux-amd64.tgz && ./ollama serve &
./ollama pull qwen2.5:3b

# 3) Agents worker（Python 3.10 + 清华源）
pip install livekit-agents==1.8.3
export LIVEKIT_URL=ws://localhost:7880 LIVEKIT_API_KEY=devkey LIVEKIT_API_SECRET=secret
python -u agent.py start &

# 4) Web + Token 服务
cd web && npm install && node server.js &

# 5) LiveTalking 数字人（模型权重走 Google Drive，云端几秒完成，本地无法下载）
python -u app.py --transport webrtc --model wav2lip --avatar_id wav2lip256_avatar1 &
```

> 注意：`livekit-server --dev` 已隐含 `devkey/secret`，再传 `--keys devkey=secret` 会报 `needs to be exactly, key: secret` 格式错误。

## 4. 角色操作步骤（实测截图）

### 4.1 客户：提问 → AI 应答

1. 打开 `https://...-3210.container.x-gpu.com/?name=customer`
2. 点「开始服务」→ 页面自动取 token、连 wss、创建 dispatch，AI 客服入房后提示「客服已接入」
3. 输入问题，回车或点「发送」

![客户-AI回复与转写广播](evidence/08-客户-AI问答与转写广播.png)

同一条答案有两条呈现路径：
- `AI客服: ...` —— RPC 同步返回值（`performRpc(method:'ask')`）
- `[转写] customer 问: ... AI 答: ...` —— agent 向房间广播的转写文本流，所有在房成员可见

### 4.2 人工坐席：旁听 + 接管外呼

1. 第二个浏览器（或无痕窗口）打开 `?name=human-seat`
2. 点「以「human-seat」加入」，无需任何操作，客户每次问答都会以 `[转写]` 落到坐席面板
3. **接管**：坐席在输入框写话术点「发送」，即以 `sendText(topic='transcript')` 广播，客户和质检同时收到

```js
// 非客户角色的发送逻辑（web/index.html）
await room.localParticipant.sendText(`[${ROLE}] ${text}`, { topic: 'transcript', destinationIdentities: [] });
```

前端按角色分流的完整实现见 `web/index.html`：`IS_CUSTOMER` 决定走 RPC 还是广播；广播的回声在 transcript handler 里用 `sender === local.identity` 过滤，避免自己看到两条。

![管理员-LiveTalking控制台](evidence/05-管理员-LiveTalking控制台.png)

### 5.2 GPU 占用（nvidia-smi 实测）

```
NVIDIA GeForce RTX 4090 D   memory.used 2542 MiB / 24564 MiB
```

### 5.3 画面取证：服务器环回抓帧

浏览器侧因 §2 的 UDP 限制拿不到画面，因此在**同一台服务器内**跑一个 aiortc 环回客户端：向 `127.0.0.1:8010/offer` 提交 SDP、从 `/api/admin/sessions` 取 sessionid、用 `/human` 驱动播报，再把收到的 RTP 帧落盘。

```bash
python -u lt_loopback.py     # 输出 /root/aics/frames/lt_*.jpg
```

实测结果：连接 `connected`，收到 `sendonly` 的音视频轨，连续取到 7 帧，帧间平均像素差 5.8–6.8（嘴部区域 2.8–3.3），证明是**实时渲染而非静止图**。

![数字人-GPU口型序列](evidence/04-数字人-GPU口型序列.jpg)

### 5.5 数字人 ↔ 文字会话 同屏联动（本轮加测）

**目标**：§5.3 的口型帧只证明"GPU 在渲染"，客户看到的仍是纯文字面板。本轮尝试把数字人画面与文字会话放进同一屏。

**通路**（全程不经浏览器 UDP）：

```
LiveTalking(GPU, 127.0.0.1:8010)
   └─ aiortc 环回观看者 avatar_bridge.py（常驻，recvonly）
        └─ 原子落盘 /root/aics/frames/latest.jpg（限流 ≈3fps）
             └─ web/server.js  /avatar.mjpeg（multipart/x-mixed-replace）
                  └─ 浏览器 <img id="avatar">   ← 与聊天面板同屏
```

**联动触发**：agent 在 RPC 应答后，把答案文本 POST 给同机 LiveTalking：

```python
sess = _get_json(AVATAR_URL + "/api/admin/sessions")
sid  = sess["data"]["sessions"][-1]["sessionid"]
_post_json(AVATAR_URL + "/human", {"sessionid": sid, "text": answer[:160], "type": "echo"})
```

**浏览器侧结果（Playwright + Chromium，1280×900）**：`<img>` 的 `naturalWidth×naturalHeight = 576×768`，即浏览器确实渲染了 LiveTalking 帧；连续 14 次采样 JPEG 体积在 55.8–61.0 KB 之间波动，画面在动。同屏截图见 `12_linkage_03_same_screen.png`：客户提问、AI 答、`[数字人] 已驱动口型播报（avatar session=e147a803…）` 与左侧数字人画面在一屏内。

**"是否真的被文字驱动"的量化判据**（`mouth_seq.py`，服务器侧对 `latest.jpg` 逐帧算差分）：

| 阶段 | 口部 ROI 相对首帧差分 | 口部 ROI 平均亮度 |
|------|----------------------|------------------|
| 播报前基线 12 帧 | mean **5.31** / max 13.57 | 113–115 |
| 播报期 45 帧 | mean **8.01**（1.51×）/ max 13.31 | 108–113（张口露暗腔） |

同一时刻 LiveTalking 日志确认 `edge tts time:1.94s → tts audio stream 24000: (331200,)`，即 331200/24000 ≈ **13.8s** 语音被合成，与 45 帧 ×0.3s ≈ 13.5s 的观测窗对齐。

**肉眼复核**（`12_linkage_05_mouth_contact_sheet.png`，8 张人脸裁切）：`pre_00`/`pre_08` 双唇闭合，`say_13`/`say_20` 明显张开露齿，`say_30` 收拢成圆唇（"乌/哦"音形），`say_44` 回落近闭 —— 口型随文本变化，不是随机抖动。

**结论（如实）**：联动**成立**，但通道是**降级**的 —— ≈3fps、**无音频**、非实时 WebRTC。生产要么给服务器开公网 UDP/TCP（或 coturn），要么把数字人视频回灌进 LiveKit 房间由 SFU 分发（见 §7 末段）。

**本轮新增踩坑**：

| 现象 | 根因 | 修法 |
|------|------|------|
| `cv2.error: could not find a writer for the specified extension` | 原子写盘用 `latest.jpg.tmp`，OpenCV 按**扩展名**选编码器 | 临时文件改名 `.latest.tmp.jpg` 再 `os.replace` |
| 重启后 `nohup ./livekit-server: Permission denied` | 仙宫云把大文件放 `/.xgcos/.links/` 对象存储挂载，软链目标重启后是 `-rw-r--r--`，**丢 exec 位** | `cp` 到本地盘 `/root/bin_livekit-server` + `chmod +x`，再软链到 `/usr/local/bin` |
| LiveKit 未起 → agent `failed to connect after 16 attempts`、web 进程 `ECONNREFUSED 127.0.0.1:7880` 未捕获异常直接退出 | 部署脚本第 3 步静默失败，第 4/5 步没有前置校验 | 每步起完必须 `ss -tln` 断言端口，再进下一步 |
| 口部差分前后完全无差异（3.64 vs 3.43） | ROI 取 `y∈[0.50,0.85]`，这个 576×768 竖屏 avatar 的**嘴在 y≈0.37**，取到的是裙摆 | 先 dump 一张全帧定位人脸，再定 ROI（本例 `y∈[0.30,0.45] x∈[0.30,0.58]`） |
| 用"帧 JPEG 是否不同"当口型判据 | LiveTalking 的 idle 视频本身就在循环动，帧永远不同 | 判据换成**口部 ROI 差分 + 亮度**，并配肉眼裁切 |

### 5.6 信令方向坑（复现时必看）

`/offer` 的 SDP 中客户端轨道必须是 **recvonly**。若写成 sendonly，服务端 `aiortc` 在 `setLocalDescription` 里做方向与运算时会抛 `ValueError: None is not in list`，HTTP 直接 500。

```js
pc.addTransceiver('video', { direction: 'recvonly' });
pc.addTransceiver('audio', { direction: 'recvonly' });
```

## 6. 转写广播与多角色踩过的坑（已修）

| 现象 | 根因 | 修法 |
|------|------|------|
| agent 发了 `[转写]`，Python 客户端收不到 | `send_text()` 默认 `topic=''`，SDK 日志 `ignoring text stream with topic '', no callback attached` | 显式传 topic |
| topic 用 `lk.chat` 后 Python 收到、浏览器仍收不到 | `lk.chat` 被 livekit-client 官方聊天协议（protobuf ChatMessage）占用，纯文本被静默丢弃 | 换自定义 topic `transcript` |
| 浏览器 handler 触发了但内容不显示 | web SDK `reader.readAll()` 返回 **string**，`new TextDecoder().decode(string)` 抛类型错 | 判类型后再解码 |
| 坐席自己发的话在面板里出现两条 | 广播回声与本地 `log('我: …')` 叠加 | transcript handler 里 `sender === local.identity` 直接 return |
| 第二个同名参与者入房后"消失"，服务端列表里没有它 | 对同一 identity 再次 `connect()`（脚本里点了两次 join）会触发重复身份互踢，先连的被断开 | 一个身份只连一次；需要多实例时换 identity（实测用 `quality-admin-2`） |

最终前端代码：

```js
room.registerTextStreamHandler('transcript', async (reader, participant) => {
  const raw = await reader.readAll();
  const txt = typeof raw === 'string' ? raw : new TextDecoder().decode(raw);
  const sender = participant ? String(participant.identity) : '';
  if (sender === String(room.localParticipant.identity)) return;   // 过滤自己的回声
  log(txt, 'bot');
});
```

另有一处健壮性修复：房间里可能残留多个历史 `agent-*` 参与者，RPC 打到僵尸实例会 `Connection timeout`。前端改为按 `joinedAt` 取**最新**的 agent：

```js
agents.sort((a, b) => (a.joinedAt?.getTime() || 0) - (b.joinedAt?.getTime() || 0));
agentIdentity = agents[agents.length - 1].identity;
```

## 7. 实测性能与已知限制

| 项 | 实测值 | 说明 |
|----|--------|------|
| AI 首答延迟 | 约 30s（冷）/ **0.8–8.4s**（热） | 冷启动加载 3B 权重；模型常驻后本轮两次实测 8.4s、0.8s |
| AI 后续问答 | 约 3s | 模型常驻显存 |
| LiveTalking 显存 | 2532 MiB（本轮实测 2540 MiB） | 4090D 单实例 |
| 坐席接管外呼 | **已跑通** | `sendText` 广播，客户/质检实时可见（图 09、10） |
| 接管后 AI 是否静默 | **未实现** | 坐席发言后客户再提问，AI 仍照常应答 —— PRD §3.1"人工接管后 AI 停止自动回复"是缺口，需服务端加会话状态位 |
| 转写是否可回放 | **否** | 文本流只投递给"当时在房"的成员，后入房的坐席看不到之前的问答 |
| 会话隔离 | 单共享房间 | 所有角色进 `cs-demo`，验证的是"多参与者同房"；PRD 的"每会话独立 agent 实例"要靠 dispatch/多房间，未在本 demo 覆盖 |
| 浏览器直连数字人画面 | **不通** | 仙宫云代理不转发 UDP，WebRTC 媒体无法穿越 |
| 数字人↔文字同屏联动 | **已跑通（降级通道）** | MJPEG 回灌：≈3fps、无音频；口部 ROI 差分 5.31→8.01（1.51×）+ 肉眼口型裁切复核，详见 §5.5 |
| 语音 ASR | **未启用** | LiveTalking 提示 `funasr not installed`，仅文字驱动播报 |
| 转写广播 | 已修复并验证 | 见 §6 |
| 僵尸 agent 参与者 | 存在 | 前端已按最新 joinedAt 选择；服务端可 `removeParticipant` 清理 |
| 计费 | ¥1.59/小时 | 余额 ¥19.38，用完须及时关机 |

**要在真实网络里跑通数字人画面**，需要以下任一条件（本次环境都不具备）：公网直连 UDP/TCP 端口的服务器、LiveKit Cloud / 自建 coturn 中继、或把数字人视频回灌进 LiveKit 房间由 SFU 分发。

## 8. 收尾清单

1. 关闭房间成员：`bash deploy/remote/kick-all.sh`（服务端 `removeParticipant`）
2. 停止实例：云控制台 → 关机（**必须**，否则按小时持续计费；关机后仅按磁盘计费）
3. **凭据卫生**：本仓库不含任何账号/密码/令牌/实例 ID（已用 `git grep --cached` 全文扫描确认）。若在本地复现时把凭据写进脚本或 `.env`，务必加入 `.gitignore`，测试后立即改密、重生成令牌与 PAT。
4. 大文件注意：部分云厂商把对象存储挂载进容器，重启后软链目标会**丢 exec 位**（§5.5 踩坑表第 2 行）。二进制请 `cp` 到本地盘再 `chmod +x`，别直接执行挂载路径。
